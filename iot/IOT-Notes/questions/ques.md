### Section 1 – Based on `iot-7.md` (Networking, CoAP/MQTT, RPL)

Scenario:  
A national park authority deploys thousands of battery-powered environmental sensor nodes (measuring temperature, humidity, and air quality) across remote forest areas. These nodes must forward their readings over a multi-hop low-power wireless network to a few gateways at ranger stations, which then send the data over the Internet to a central cloud service for long-term storage and analysis.

Question:  
For this national-park monitoring system, explain how a single sensor reading travels from a leaf node all the way to the cloud in terms of the communication stack, describing what happens at the transport, network, and link layers as data is encapsulated and decapsulated at each hop. Which transport protocol and which IoT application protocol would you choose for the constrained sensor nodes (e.g., combinations of TCP/UDP with CoAP or MQTT), and why are they appropriate in terms of reliability, overhead, and energy use? In this many-sensors-to-one-gateway topology, which routing method would you use among the low-power nodes, and how does that method organize the network (e.g., using a DODAG and specific control messages) to let new nodes join and maintain routes despite lossy wireless links?

Answer:
**Answer (Section 1):**

A single sensor reading starts at the application on the leaf node, which formats the measurement as a small payload (e.g., a resource like `/sensors/temp` with a numeric value). This payload is given to the transport layer, which (on a constrained node) uses **UDP** to create a datagram with a minimal header and no connection setup. The UDP segment is then passed to the **network layer**, where it gets an **IPv6** header; over a low‑power radio, this header is usually compressed by an adaptation layer (e.g., 6LoWPAN) to save bytes. Finally, the **link layer** (e.g., IEEE 802.15.4) wraps the network packet in a frame with its own header and trailer and transmits it over the physical radio channel to the next hop.

At each intermediate sensor/router on the way to the gateway, the **link layer decapsulates and re‑encapsulates** the frame: it receives a frame, checks it, strips the link header/trailer, and passes the IPv6/UDP/CoAP packet up to the network layer. The network layer forwards the packet according to its routing table, handing the same IPv6/UDP/CoAP packet down to the link layer toward the chosen next hop. Only the **link‑layer envelope** changes at each hop; the transport and application payload remain the same. At the **gateway**, the last low‑power hop is decapsulated, and the IPv6/UDP/CoAP message is forwarded onto the wider Internet (possibly translated or proxied to HTTP/REST) over a higher‑capacity network (Ethernet/Wi‑Fi) to the cloud server, where the application decapsulates the CoAP message and stores or processes the reading.

For the constrained forest sensors, I would choose **UDP as the transport protocol and CoAP as the application protocol**. UDP avoids connection setup, large state, and heavy congestion‑control mechanisms that make **TCP** expensive on tiny, battery‑powered nodes with lossy links. **CoAP** is explicitly designed for constrained environments: it is REST‑like (similar to HTTP), uses a very small base header, and supports **confirmable messages** for lightweight reliability over UDP instead of a full TCP stack. This combination minimizes **header overhead, memory usage, and energy consumption**, while still giving a clean request/response interface that can be translated to HTTP at the gateway.

For routing between many low‑power nodes and a few gateways in a many‑to‑one topology, I would use **RPL (Routing Protocol for Low‑Power and Lossy Networks)**. RPL organizes the network into a **Destination Oriented Directed Acyclic Graph (DODAG)** rooted at the gateway. The root periodically sends **DIO (DODAG Information Object)** messages downward to advertise the existence and properties of the DODAG (objective function, version, grounded/floating status, etc.). New nodes that hear nothing can first send **DIS (DODAG Information Solicitation)** to ask neighbors to advertise any existing DODAGs. When a node receives DIOs, it computes its **rank** using the objective function (e.g., hop count, link quality, energy cost) and chooses one or more parents that minimize this rank. It then sends **DAO (Destination Advertisement Object)** messages upward (with DAO‑ACK responses) to announce that it and possibly its descendants are reachable via those parents. In this way, RPL automatically lets new nodes join, maintains upward routes from sensors to the root, and can repair or update the DODAG when links are lossy or the topology changes, which is exactly what is needed in a large, unreliable forest deployment.

### Section 2 – Based on `iot-7.5.md` (Link/Physical, IEEE 802.15.4, 6LoWPAN)

Scenario:  
An industrial company wants to retrofit a large factory with wireless vibration and temperature sensors on hundreds of machines. Each sensor must run for several years on a small battery and is installed in a noisy RF environment where a standard Wi‑Fi network is already in use for laptops and cameras. The company also needs to eventually access each sensor over IPv6 from its monitoring center.

Question:  
Design the local wireless network for these factory sensors. Which link-layer technology would you choose instead of simply putting every sensor on Wi‑Fi or a power-line system, and what properties of that technology make it better suited for low-power, low-data-rate IoT nodes? Describe how a time-division and beacon-based access method with configurable duty cycles can be used so sensors mostly sleep, wake up only in defined time slots, and still exchange frames reliably while avoiding interference. Finally, explain which adaptation method you would place above this link layer so that full IPv6 packets can be carried efficiently on small, low-power frames, and what specific mechanisms (such as header compression and fragmentation/reassembly) this method uses to make IPv6 practical in this environment.

Answer:
**Answer**

I would design the local wireless network around an **IEEE 802.15.4–based low‑power mesh** instead of Wi‑Fi or power‑line technologies. IEEE 802.15.4 radios are optimized for **low data rate, low cost, and very low energy consumption**, which matches battery‑powered vibration/temperature sensors that only send small, infrequent measurements. Compared to Wi‑Fi, they have much **lower transmit power and simpler PHY/MAC**, so nodes can sleep most of the time and still communicate reliably at short range. Power‑line systems like X10 are slow, noisy, and not well suited to dense, mobile, RF‑noisy industrial environments, while 802.15.4 has well‑defined mechanisms for multi‑hop sensor networks and coexists better with existing infrastructure when channels are chosen carefully.

At the MAC level I would enable a **time‑division, beacon‑based access scheme** with a central coordinator (or a small number of coordinators) per factory area. The coordinator periodically transmits **beacons** that define a **superframe** divided into time slots; each sensor synchronizes its clock from these beacons. Sensors are configured with **assigned slots** (or groups of slots) when they are allowed to send/receive, and can put their radios into **deep sleep for the rest of the superframe**, dramatically cutting idle‑listening energy. By tuning the **beacon interval and duty cycle**, we can trade off latency against battery life: infrequent beacons and short active periods for long‑lived sensors, more frequent beacons where tighter real‑time behavior is required. To deal with the noisy RF environment and existing Wi‑Fi, the coordinator selects **non‑overlapping channels** in the 2.4 GHz band (or a sub‑GHz 802.15.4 variant) and uses link‑layer **retransmissions (ARQ)** so that occasional collisions or interference do not cause permanent data loss.

Above this link layer I would deploy **6LoWPAN as an adaptation layer** so that each sensor can still use **full IPv6 addressing** without wasting scarce frame space. 6LoWPAN performs **header compression**, exploiting the fact that many IPv6 header fields (prefixes, flow labels, next‑header values, etc.) are constant or predictable within a WSN; in common cases it can shrink a 40‑byte IPv6 header down to just a few bytes, plus similarly compressed UDP information. It also provides **fragmentation and reassembly**, splitting large IPv6 packets into multiple 802.15.4 frames and tagging them so the receiver can reconstruct the original packet despite the tiny MTU. With these mechanisms, each battery‑powered sensor can participate in a **true IPv6 network**, reachable from the monitoring center, while the radio on the factory floor only ever sends **small, efficient frames** suitable for low‑power, lossy links.
